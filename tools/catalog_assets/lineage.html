From ODCS contracts to a data catalog

Our contracts are enough to build the catalog and its lineage. No dbt, no database, no SQL parsing.

The code that creates the JSON: tools/build_catalog.py (function build_manifest). The result: colibri-manifest.json.

1. One ODCS contract per table

Each contract becomes a catalog node, with its sheet and columns.

Which ODCS field becomes what?
In the contractIn the catalog
idthe node identifier
serversthe project and dataset the table is filed under
schema.propertiesthe columns, including nested fields
physicalType, logicalType, descriptionthe column types and description
classification, tagsthe column labels
qualitythe quality checks block
version, team, slaProperties, supportthe table sheet

2. transformSourceObjects: where each column comes from

ODCS provides this field on every column: a list of free-form strings. Our convention: contract#object.column, where contract is the id of the source contract and object the name of the table in its schema.

# acquisition_monthly.odcs.yaml (excerpt)
- name: spend_amount
  transformLogic: transform
  transformSourceObjects:
    - core__ad_spend#ad_spend.spend_eur
    - core__ad_spend#ad_spend.spend_date
    - core__ad_spend#ad_spend.platform
    - core__ad_spend#ad_spend.campaign_id
  customProperties:
    - property: transformExpression
      value: IFNULL(SUM(spend_eur), 0)

The spend is the sum of spend_eur. The three other columns group it by month, channel and campaign: they are cited too, not only the one in the expression.

Our writing rules
  • A nested field is written with its path: raw__refunds__shopify#refunds.transactions.amount.
  • transformExpression: the BigQuery SQL, our own property in customProperties. It is displayed, never run.
transformLogicSourcesExpression

What about raw tables?

The source is the external system, for example shopify_admin_api#Order.id. It is not a contract of this repository: no arrow is drawn and the reference only appears in the contract YAML. Each top-level raw field copied from the source is still marked P (pass-through).

3. Each reference between contracts becomes an arrow

core__ad_spend # ad_spend . spend_eur
   contract       object    column

core__ad_spend.spend_eur  →  acquisition_monthly.spend_amount

Arrows between tables follow from this: nobody declares them. From raw to core and then to customer, they form the full path of a number.

What the JSON contains 
{
  "metadata": { ... },
  "nodes":    { "acquisition_monthly": { "columns": { ... } }, ... },
  "lineage":  { "edges": [ ... ], "parents": { ... }, "children": { ... } },
  "tree":     { "byDatabase": { ... }, "byPath": { ... } }
}

// one entry of lineage.edges
{"id": 1,
 "source": "core__ad_spend",      "sourceColumn": "spend_eur",
 "target": "acquisition_monthly", "targetColumn": "spend_amount"}

The site receives metadata, nodes, tree and lineage.edges; parents and children stay in the JSON file only. edges holds one entry per arrow between columns, plus one per pair of linked tables (empty columns).

4. Verify, then generate

make check checks the contracts (and runs the tests), including that columns cited by core and customer exist (for raw, only the external system name is checked). make catalog runs the contract checks again (schema and references) and stops if they fail. Otherwise it writes the JSON and injects it into the dbt-colibri interface (MIT license), without dbt: that is the catalog.

Limit: nothing proves that the SQL uses the declared sources.

Des contrats ODCS au data catalogue

Nos contrats suffisent à construire le catalogue et son lineage. Ni dbt, ni base de données, ni analyse du SQL.

Le code qui crée le JSON : tools/build_catalog.py (fonction build_manifest). Le résultat : colibri-manifest.json.

1. Un contrat ODCS par table

Chaque contrat devient un nœud du catalogue, avec sa fiche et ses colonnes.

Quel champ ODCS devient quoi ?

2. transformSourceObjects : d'où vient chaque colonne

ODCS prévoit ce champ sur chaque colonne : une liste de chaînes libres. Notre convention : contrat#objet.colonne, où contrat est l'id du contrat source et objet le name de la table dans son schema.

# acquisition_monthly.odcs.yaml (extrait)
- name: spend_amount
  transformLogic: transform
  transformSourceObjects:
    - core__ad_spend#ad_spend.spend_eur
    - core__ad_spend#ad_spend.spend_date
    - core__ad_spend#ad_spend.platform
    - core__ad_spend#ad_spend.campaign_id
  customProperties:
    - property: transformExpression
      value: IFNULL(SUM(spend_eur), 0)

La dépense est la somme de spend_eur. Les trois autres colonnes servent à la grouper par mois, canal et campagne : elles sont citées aussi, pas seulement celle de l'expression.

Nos règles d'écriture
  • Un champ imbriqué s'écrit avec son chemin : raw__refunds__shopify#refunds.transactions.amount.
  • transformExpression : le SQL BigQuery, propriété maison dans customProperties. Il est affiché, jamais exécuté.

Et pour les tables raw ?

La source est le système externe, par exemple shopify_admin_api#Order.id. Ce n'est pas un contrat du dépôt : aucune flèche n'est dessinée et la référence ne figure que dans le YAML du contrat. Chaque champ raw de premier niveau recopié de la source est tout de même marqué P (pass-through, recopie).

3. Chaque référence entre contrats devient une flèche

core__ad_spend # ad_spend . spend_eur
   contrat        objet     colonne

core__ad_spend.spend_eur  →  acquisition_monthly.spend_amount

Les flèches entre tables en découlent : personne ne les déclare. De raw à core puis à customer, elles forment le chemin complet d'un chiffre.

Ce que contient le JSON 
{
  "metadata": { ... },
  "nodes":    { "acquisition_monthly": { "columns": { ... } }, ... },
  "lineage":  { "edges": [ ... ], "parents": { ... }, "children": { ... } },
  "tree":     { "byDatabase": { ... }, "byPath": { ... } }
}

// une entrée de lineage.edges
{"id": 1,
 "source": "core__ad_spend",      "sourceColumn": "spend_eur",
 "target": "acquisition_monthly", "targetColumn": "spend_amount"}

Le site reçoit metadata, nodes, tree et lineage.edges ; parents et children ne restent que dans le fichier JSON. edges contient une entrée par flèche entre colonnes, plus une par paire de tables liées (colonnes vides).

4. Vérifier, puis générer

make check contrôle les contrats (et lance les tests), dont l'existence des colonnes citées par core et customer (pour les raw, seul le nom du système externe est contrôlé). make catalog refait les contrôles des contrats (schéma et références) et s'arrête s'ils échouent. Sinon, il écrit le JSON et l'injecte dans l'interface de dbt-colibri (licence MIT), sans dbt : c'est le catalogue.

Limite : rien ne prouve que le SQL utilise les sources déclarées.
